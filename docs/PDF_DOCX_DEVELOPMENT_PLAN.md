## 1. 목표와 범위

PDF → DOCX와 DOCX → PDF를 메인 프로그램과 탐색기 우클릭 단일 파일 변환에 추가한다. 원본 보존, 결과 이름 충돌 시 번호 추가, 임시 파일 정리, 기존 일괄 작업·취소 처리를 유지한다.

사용자 요구에 따라 완전 보존 가능한 변환은 `XXX로 변환`, 내용·서식·구조가 달라질 수 있지만 결과를 만들 수 있는 변환은 `XXX로 불완전 변환`으로 표시한다. 실행 불가능과 품질 제한을 구분한다.

이번 범위에 DOC, DOCM, HWP, OCR, 클라우드 변환, 탐색기 다중 선택, 새 셸 확장, 자동 품질 점수 기능은 포함하지 않는다. 메인 프로그램의 기존 여러 파일 변환은 새 형식에도 적용한다. 실제 개발·커밋·배포는 이 문서 작성 작업에 포함하지 않는다.

## 3. ‘변환’과 ‘불완전 변환’ 정책

### 3.1 표시 기준

- `변환`: 해당 변환 방식의 지원 범위에서 내용·품질·구조 보존을 보장할 근거가 있는 경우.
- `불완전 변환`: 변환은 지원하지만 글꼴, 배치, 표, 편집 구조 또는 문서 기능이 달라질 수 있는 경우.
- `실패`: 엔진 미설치, 암호, 손상, 시간 초과, 읽을 수 없는 결과 등으로 유효한 출력이 없는 경우. 불완전 변환 성공으로 처리하지 않는다.

| 방향 | 이번 버전 메뉴 | 근거 |
| --- | --- | --- |
| PDF → DOCX | `DOCX로 불완전 변환` | 고정 배치에서 문단·표·읽기 순서 등을 재구성하므로 원본 구조 복원을 보장할 수 없음 |
| DOCX → PDF | `PDF로 불완전 변환` | 글꼴·렌더러 차이가 있을 수 있고 Word 편집 구조·일부 문서 기능이 보존되지 않음 |

DOCX→PDF도 일반적인 인쇄 모양은 잘 보존할 수 있지만 모든 문서의 완전 보존을 의미하지 않는다. Word 설치 여부나 출력 파일 생성 성공만으로 `변환`으로 승격하지 않는다. 기존 PPT→PDF의 보수적 판정과도 일치한다.

현재 탐색기 메뉴는 확장자별 정적 등록이다. 우클릭한 개별 파일을 미리 분석해 문구를 바꾸는 구조가 아니다. 이번에는 변환 방식별로 판정하고, 파일별 제한과 실패는 선택 후 검사한다. 개별 파일의 완전성을 자동 판정하는 동적 셸 확장은 별도 범위다.

### 3.2 UI 규칙

- 기존 `imperfect_for_extension()`을 단일 판정 위치로 유지한다. 두 방향에 `True`를 반환하고 대소문자·점 접두사 정규화를 유지한다.
- 기존 번역 키 `{v0}로 변환`, `{v0}로 불완전 변환`을 재사용한다. 내부 형식 값은 계속 `docx`, `pdf`다.
- 메인 형식 선택과 탐색기 메뉴는 같은 문구를 사용한다. 우클릭 창에도 품질 제한을 표시한다.
- 완료는 ‘파일 생성 및 유효성 검증 성공’을 뜻한다. 완료 뒤에도 불완전 변환 고지를 지우거나 완전 복원이라고 안내하지 않는다.
- 반복 확인 팝업 대신 작업 설명이나 상세 안내를 사용한다. 불완전 변환을 빨간 실패 상태로 표시하지 않는다.
- 기존 다른 형식의 판정은 이번 변경에서 수정하지 않는다.

## 4. 변환 엔진 결정

새 대형 변환 라이브러리를 추가하기보다 기존 외부 Office 연동 방식에 맞춰 시작한다.

| 방향 | 우선 엔진 | 대체 경로 | 설치되지 않은 경우 |
| --- | --- | --- | --- |
| DOCX → PDF | Microsoft Word COM | LibreOffice Writer PDF 내보내기 | Word 또는 LibreOffice 설치 안내 |
| PDF → DOCX | 내장 PDF 텍스트·페이지 이미지 추출 | Word PDF 가져오기는 대체 경로로 보류 | OCR 없이 이미지 중심 결과 안내 |

초기 실험에서 Word의 PDF 가져오기가 숨은 대화상자에서 시간 초과했으므로, PDF→DOCX는 내장 PDF 텍스트 추출과 페이지 이미지 삽입 경로로 구현한다. LibreOffice의 PDF 가져오기를 편집 가능한 Writer DOCX 복원으로 간주하지 않는다. OCR은 제공하지 않는다.

설치 확인은 후보 탐색일 뿐 성공 보장이 아니다. 실제 COM 생성·문서 열기·내보내기를 검증한다. Office 버전과 테스트 환경을 결과 문서에 기록한다. Word가 없으면 DOCX→PDF에 LibreOffice를 선택하되, Word에서 문서 오류가 발생했다고 엔진을 무조건 바꿔 재시도하지 않는다.

### 4.1 최소 구조

- `src/document.py` 신설: DOCX 패키지 검사, 내장 PDF→DOCX 생성, Word/LibreOffice DOCX→PDF 실행, 결과 검사. 기존 PPT 전용 backend와 구분한다.
- `src/word.ps1` 신설: Word 문서 열기, PDF 내보내기, DOCX 저장, COM 정리.
- 함수 예시: `word_backend(direction)`, `docx_to_pdf(src, dst, cancel, progress)`, `pdf_to_docx(src, dst, cancel, progress)`.
- 현재 `office.py`에서 작은 공통 함수가 꼭 필요한 경우에만 추출한다. 전체 Office 프레임워크로 재설계하지 않는다.
- DOCX 패키지 검사는 표준 `zipfile`과 XML 파서를 우선 사용한다. 검증만을 위해 `python-docx`를 추가하지 않는다.

### 4.2 실행 계약

- Word: DOCX→PDF만 읽기 전용으로 열고 원본을 저장하지 않는다. PDF 출력은 `Document.ExportAsFixedFormat`를 사용한다.
- PDF 출력은 문서 본문 인쇄 기준으로 고정한다. 주석·변경 추적 표시와 외부 필드 갱신 정책을 명시적으로 정하고 샘플로 검증한다. 기본 정책은 주석/변경 추적 마크업 출력 제외, 외부 링크 자동 갱신 금지다.
- LibreOffice: `pdf:writer_pdf_Export` 필터와 작업별 임시 사용자 프로필을 사용한다. 기존 `impress_pdf_Export`를 사용하지 않는다.
- 작업은 로컬에서 실행한다. 문서 업로드나 Office 자동 설치·자동 로그인은 추가하지 않는다.
- 인자를 배열로 전달하고 파일 경로를 PowerShell 코드 문자열에 삽입하지 않는다. 한글·공백·괄호가 있는 경로를 지원한다.
- 새 도우미는 기존 방식처럼 숨김 실행하고, 표준 출력/오류를 수집한다. COM 접근 시 실행되는 매크로·외부 링크를 비활성화하고 설정은 정리 단계에서 복원한다.
- 작업이 소유한 문서만 닫는다. 기존 사용자의 Word/PowerPoint 문서 또는 전체 `WINWORD` 프로세스를 종료하지 않는다. 별도 인스턴스 소유권이 확인되는 경우에만 Quit한다.
- 취소/120초 기본 시간 제한에서 자식 helper 종료만으로 Word까지 정리됐다고 가정하지 않는다. 소유 인스턴스의 정상 정리 및 잔류 프로세스 여부를 실환경에서 확인한다. 소유권이 불명확한 프로세스를 강제 종료하지 않는다.
- 취소 시 새 결과는 최종 경로로 이동하지 않는다. 실행 중 COM 호출이 즉시 중단되지 않으면 ‘취소 처리 중’으로 표시하고 제한 시간 내 정리를 수행한다.

## 5. 입력·출력 검증과 제한

### DOCX → PDF

1. 파일 존재·비어 있지 않음을 확인한다.
2. DOCX ZIP 패키지의 `[Content_Types].xml`, `_rels/.rels`, Word 본문 파트와 관계를 확인한다. 암호화된 Office 파일은 일반 ZIP 검사가 실패할 수 있으므로 암호/손상 가능성을 정확하게 안내한다.
3. DOCX를 `kind='document'`, `formats=['pdf']`로 등록한다. 파일을 ZIP으로 풀어 디스크에 전개할 필요는 없다.
4. 엔진에서 PDF를 임시 경로로 생성한 뒤 PyMuPDF로 열림·1페이지 이상을 확인한다.
5. 유효한 빈 Word 문서의 빈 PDF 페이지는 실패로 오인하지 않는다. 텍스트 길이만으로 성공을 판정하지 않는다.

### PDF → DOCX

1. 기존 PDF 암호·페이지 검사를 유지한다. PDF에 `docx` 출력 형식을 추가한다.
2. 내장 변환기가 페이지 텍스트를 문단으로 만들고 텍스트 없는 페이지는 이미지로 삽입한다. 생성된 파일의 ZIP/필수 XML·관계를 확인한다. 파일 크기가 0보다 크다는 이유만으로 성공 처리하지 않는다.
3. 본문 텍스트와 이미지·도형 등 콘텐츠 유무를 확인한다. 원본에 내용이 있는데 결과 본문과 시각 콘텐츠가 모두 없는 경우 실패 처리한다. 단순 텍스트 개수 비교는 참고 정보이며 의미 보존 증명이 아니다.
4. 텍스트가 거의 없거나 이미지 위주인 PDF에는 ‘텍스트가 편집 가능한 형태로 복원되지 않을 수 있습니다. OCR은 지원하지 않습니다.’를 안내한다. 텍스트가 없다는 사실만으로 무조건 스캔이라고 단정하지 않는다.
5. 이미지로만 생성된 DOCX는 이미지 중심 결과임을 알린다. 편집 가능한 텍스트 복원 성공이라고 표현하지 않는다. 변환 엔진이 처리하지 못하면 실패로 표시한다.

두 방향 모두 원본 덮어쓰기 금지, 결과 이름 자동 번호, 임시 폴더 사용은 `engine.convert()`의 기존 흐름을 재사용한다. 여러 우클릭 프로세스가 같은 출력 이름을 사용할 때도 기존 rename 충돌 처리를 유지한다.

- [ ] 새 의존성을 추가했다면 버전·라이선스·고지를 기록한다. 이번 기본 경로에는 새 Python 의존성이 필요하지 않을 것으로 예상한다.

## 7. 검증 계획

### 자동 테스트

| 대상 | 핵심 사례 |
| --- | --- |
| 엔진 | DOCX 인식, 손상/빈 파일, PDF의 DOCX 형식, 올바른 분기, 잘못된 출력 형식 거부 |
| 품질 판정 | `.DOCX`→`PDF`, `pdf`→`docx` 모두 불완전, 기존 대표 일반 변환 판정 유지 |
| 외부 실행 | Word/LO/둘 다 없음, Word 실패, exit code 0인데 출력 없음, 잘못된 DOCX/PDF 출력 |
| 취소·저장 | 시작 전 취소, 실행 중 취소, 시간 초과, 임시 결과 정리, 원본 보존, 같은 이름 번호 부여 |
| 메뉴 | PDF에 DOCX, DOCX에 PDF, 두 불완전 문구, 인자 인용, 등록/해제, 무관한 키 보존 |
| UI·번역 | 필터, 내부 format 값, 메인/우클릭 문구 일치, 16개 언어 키와 자리표시자 |

외부 Office 테스트는 mock으로 분기와 실패 처리를 검증하고, 실제 Office 품질 검증을 대체하지 않는다. 레지스트리 테스트는 기존 fake_registry를 사용한다.

### 실환경 검증

- Word만 설치 / LibreOffice만 설치 / 둘 다 설치 / 둘 다 없음 환경의 동작을 확인한다. LO만 있을 때 PDF→DOCX는 명확한 설치 안내가 나와야 한다.
- 한글·영문·혼합 글꼴, 표·병합 셀, 이미지, 머리말·꼬리말, 다중 페이지, 다단, 수식, 주석·변경 추적 샘플을 확인한다.
- 텍스트 PDF, 스캔 PDF, 텍스트+이미지 혼합 PDF, 회전/혼합 크기 페이지를 확인한다.
- 암호·손상 파일, 한글·공백 경로, 쓰기 불가 폴더, 출력 이름 충돌, 열려 있는 원본을 확인한다.
- 결과를 실제 Word/PDF 뷰어로 열어 페이지·내용 누락, 표/이미지 위치, 한글 깨짐, 편집 가능 여부를 확인한다. PDF→DOCX의 페이지 수 차이만으로 실패 처리하지 않는다.
- 사용자가 Word 문서를 연 상태에서 완료·취소·시간 초과를 재현하고 사용자 문서와 프로세스가 보존되는지 확인한다.
- Windows 10/11 탐색기 실제 메뉴 및 Windows 11 ‘더 많은 옵션 표시’ 경로를 확인한다.
- 포터블 EXE에서 두 방향, 미설치 오류, 취소, 메뉴 재등록을 검증한다. Python 없는 환경에서도 확인한다.

기본 명령은 프로젝트 루트에서 다음과 같다.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m PyInstaller --noconfirm "Simple File Converter.spec"
& ".\dist\Simple File Converter.exe" --self-test ".\build\smoke-check"
& ".\dist\Simple File Converter.exe" --smoke-test
```

가상환경이 없다면 `docs/DEVELOPMENT.md`의 준비 절차를 따른다. 테스트하지 못한 환경은 ‘미검증’으로 기록한다.

## 8. 최종 완료 기준과 luna 인계

- [ ] 두 방향 모두 메인 프로그램과 탐색기 단일 파일 메뉴에서 실행된다.
- [ ] 두 방향의 메뉴에 정확히 `DOCX로 불완전 변환`, `PDF로 불완전 변환`이 표시된다.
- [ ] 기존 일반 변환 문구·변환 기능은 유지된다.
- [ ] 지원 환경에서 읽을 수 있는 결과가 만들어지고 원본·기존 결과는 보존된다.
- [ ] 미설치·손상·암호·취소·시간 초과를 성공으로 잘못 표시하지 않는다.
- [ ] 이미지 중심 DOCX를 편집 가능한 텍스트 복원으로 안내하지 않는다.
- [ ] 기존 테스트, 신규 테스트, 실제 Office 변환, 탐색기, EXE 확인 결과를 각각 기록한다.
- [ ] 변경 파일·검증 환경·남은 제한을 최종 보고한다. mock 테스트 통과만으로 실변환 검증을 완료했다고 보고하지 않는다.

luna는 이 문서를 읽고 1단계 최소 실험부터 시작한다. 우선 DOCX→PDF, 다음 PDF→DOCX, 이후 UI/메뉴와 배포 검증 순서로 진행한다. 구현 중 사용자가 별도 범위를 지정하지 않는 한 DOC/OCR/동적 메뉴/다중 선택까지 확장하지 않는다. 이 문서는 개발 인계용이며 게시·push·릴리스 업로드 지시가 아니다.

## 9. 기술 근거

- [Microsoft — Opening PDFs in Word](https://support.microsoft.com/en-us/word/opening-pdfs-in-word): PDF는 원본 문단·표 구조를 그대로 제공하지 않으며 Word가 이를 재구성한다. PDF→DOCX 불완전 표시의 근거.
- [Microsoft — Document.ExportAsFixedFormat](https://learn.microsoft.com/en-us/office/vba/api/word.document.exportasfixedformat): Word PDF 내보내기 API. 구현 시 매개변수와 출력 정책 확인.
- [LibreOffice — Starting with parameters](https://help.libreoffice.org/latest/en-GB/text/shared/guide/start_parameters.html): headless, convert-to 및 출력 경로 지정. Writer 필터 사용과 독립 프로필 실행을 검증할 때 참고.

위 문서는 기술 경로의 근거이며 개별 파일의 완전 보존을 보증하지 않는다.
