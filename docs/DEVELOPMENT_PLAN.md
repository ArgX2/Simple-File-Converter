# Simple File Converter 개발 실행 계획

작성일: 2026-09-21

이 문서는 사용량이 돌아온 뒤 개발을 재개할 때 따를 작업 순서다. 지금은 계획을 기록하는 단계이며, 아래 체크리스트는 구현 완료를 의미하지 않는다. 사용자가 말한 Word의 `docs`는 `DOC`·`DOCX`로 해석한다.

## 1. 현재 상태와 출발점

| 구분 | 현재 상태 | 다음 작업 |
| --- | --- | --- |
| 영상·음성·이미지 변환 | 기존 구현 있음 | 새 기능을 추가할 때 기존 동작 회귀 확인 |
| PDF → PNG/JPG/WEBP/TIFF | 기존 구현 있음. 전체 페이지를 별도 폴더에 저장 | 신규 개발로 중복 처리하지 않기 |
| PDF → TXT | 이번 단계에서 구현 시작 | 페이지 순서대로 텍스트를 UTF-8 파일에 추출 |
| PNG/JPG 등 이미지 → PDF | 기존 구현 있음 | 여러 개의 독립 파일을 한 PDF로 합치는 기능과 구분 |
| PPT/PPTX → PDF | 외부 Office 연동 구현 있음 | 여러 파일 선택 시 일괄 처리 확장 |
| PDF → PPTX/PPT | 이미지 슬라이드 방식 구현 있음 | 편집 구조 제한 고지 유지 |
| 우클릭 단일 파일 변환 | 기존 구현 있음 | 다중 선택 기능의 기준 동작으로 사용 |
| 우클릭 다중 파일 변환 | 미완성 코드·테스트 변경이 작업 폴더에 남아 있음 | 아래 0단계에서 먼저 검토 |
| Word·HWP 및 PDF↔HTML/Markdown, PDF→DOCX | 요청과 후보가 기록된 상태 | 이 계획의 순서에 따라 구현·타당성 검토 |
| 다국어 | UI 16개 언어, README 5개 언어 | 기능마다 번역과 안내 동기화 |

### 남아 있는 미완성 변경

`src/app.py`, `src/quick_convert.py`, `src/shell_menu.py`, `tests/test_i18n.py`, `tests/test_shell_menu.py`에 다중 선택 시도에 따른 미커밋 변경이 있다. 이전에 “계획서만 기록”으로 전환한 뒤에도 이 변경은 실제 파일에 남아 있다. 문서 작성 과정에서는 해당 코드를 추가 수정하거나 되돌리지 않는다.

현재 코드에서 확인한 재개 시 점검 사항:

- `MultiSelectModel=Player`와 `%*`를 사용하도록 수정했지만, 탐색기에서 모든 선택 파일이 한 번에 전달되는지는 검증되지 않았다. 이것만으로 다중 선택 구현이 완료됐다고 판단하지 않는다.
- `QuickConvert.receive()`는 결과를 파일별로 누적하지 않고 마지막 결과로 덮어쓴다. 일부 실패 후 마지막 파일만 성공하면 전체 성공처럼 표시할 수 있다.
- 여러 파일일 때 표시하는 `개 파일` 문구가 한국어로 직접 작성되어 있다.
- 동일 확장자 검사와 서로 다른 형식 선택 시 처리 규칙이 아직 없다.
- 이전 테스트 실행에서는 다중 선택 관련 테스트 1개가 실패했다. 이번 문서 작성에서는 재실행하지 않았다.
- 해당 테스트는 경로 전체에 `jpg`가 포함되는지를 검사하므로, JPG 입력 그룹의 다른 출력 명령까지 JPG 출력으로 오인할 수 있다. 레지스트리 문자열 검사와 실제 탐색기 동작 검증을 구분해야 한다.

## 2. 개발 순서

**작업 상태 정리 → 형식 표시·품질 고지 정리 → PDF → TXT → 다중 선택 일괄 변환 → Word → PDF와 웹 문서 양방향 → PDF에서 Word 복원 → HWP/HWPX → 추가 후보 → 배포**

각 단계에서 해당 기능의 테스트와 번역을 함께 완료한다. 전체 기능을 다 만든 뒤 한 번에 검증하지 않는다. HWP/HWPX의 실현 가능성은 초반에 짧게 확인하되, 본 구현은 사용할 엔진과 환경이 확인된 뒤 진행한다.

## 0단계 — 작업 상태와 기준 동작 정리

- [ ] 미완성 변경과 사용자의 별도 변경을 구분하고, 미완성 부분을 계속 사용할지 검토한다. 확인 없이 변경을 일괄 폐기하지 않는다.
- [ ] 원격 커밋과 로컬 작업 상태를 확인하고, 개발 기준 커밋을 기록한다.
- [ ] 현재 테스트를 실행해 실제 실패 목록을 확인한다. 미완성 상태를 배포 대상으로 삼지 않는다.
- [ ] 단일 파일 우클릭, 원본 폴더 저장, 기존 변환, 언어 전환의 기준 동작을 확인한다.

완료 기준: 기존 기능과 미완성 기능을 명확히 구분하고, 재현 가능한 테스트 상태에서 다음 단계로 넘어간다.

## 1단계 — 출력 형식과 품질 안내 분리

현재 `app.py`는 형식 선택 상자의 `currentText()`를 변환 명령에도 사용한다. 여기에 경고 문구를 바로 붙이면 `docx (손상될 수 있음)` 전체가 형식 값으로 전달될 수 있으므로 이 부분부터 수정한다.

- [ ] 선택 상자의 표시 문구와 내부 형식 값(`docx`, `pdf` 등)을 분리한다. 내부 값은 항목 데이터에서 읽는다.
- [ ] 메인 UI·실제 변환·우클릭 메뉴가 사용하는 입력/출력 규칙을 필요한 범위에서 공유한다.
- [ ] 변환별로 지원 조건, 외부 프로그램 필요 여부, 품질 제한 문구를 정의한다.
- [ ] 새 변환 엔진은 소규모 샘플로 검증한 뒤 지원 형식 목록에 연결한다.

품질 문구는 **`(손상 가능)`**을 기본 짧은 표현으로 제안한다. 예: `DOCX로 변환 (손상 가능)`. 상세 안내에는 “원본 파일은 유지되며, 변환 결과의 글꼴·표·배치 등이 달라질 수 있습니다”라고 설명해 원본 파일이 손상된다는 오해를 줄인다.

실제 결과를 분석해 100% 동일성을 자동 판정하는 기능은 이번 범위가 아니다. 차이가 생길 수 있는 변환 방식에 미리 고지한다.

| 변환 유형 | 표시 방침 |
| --- | --- |
| PDF → DOCX/HTML/Markdown | 구조·배치 복원 제한 고지 |
| PDF → PPT/PPTX | 기존 `(이미지 슬라이드)` 안내 유지, 개별 텍스트 편집 불가 명시 |
| Word/HWP → PDF | 사용 엔진·글꼴 등에 따른 차이 가능성을 검토해 표시 |
| PDF → PNG | 페이지 이미지 출력으로 안내. DPI와 텍스트 편집·검색 불가를 설명하고 “100% 무손실 복원”으로 표현하지 않기 |
| PNG → PDF | 이미지 기반 PDF라고 안내. 편집 가능한 문서 복원으로 표현하지 않기 |
| 기존 영상·음성·이미지 변환 | 첫 프레임만 저장, 애니메이션·투명도 소실, 손실 압축 등 기존 제한도 같은 기준으로 점검 |

- [ ] 형식 선택·우클릭 메뉴·필요한 확인창·완료 상세 안내에 일관된 문구를 적용한다.
- [ ] 긴 설명은 상세 안내에 두고, 같은 작업 중 확인 팝업을 반복하지 않는다.
- [ ] 16개 언어에서 문구와 자리표시자가 일치하고, 내부 형식 값에 영향을 주지 않는지 확인한다.

완료 기준: 경고 문구나 표시 언어를 바꿔도 실제 출력 형식과 변환 결과가 달라지지 않는다.

## 2단계 — 동일 형식 파일의 우클릭 일괄 변환

목표 동작: **여러 PPTX 선택 → 우클릭 → Simple File Converter → PDF로 변환 → 각 파일의 원래 위치에 PDF 생성**. 여러 PPT를 선택한 경우도 같은 방식으로 지원한다. 이는 개별 변환이며 여러 문서를 하나의 PDF로 합치는 동작과 구분한다.

- [ ] 동일 확장자 여러 개 선택을 우선 지원한다. 대소문자만 다른 확장자는 동일하게 취급한다.
- [ ] PPT와 PPTX를 섞은 선택은 별도 지원 여부를 결정한다. 첫 단계에서 자동으로 같은 형식으로 간주하지 않는다.
- [ ] 탐색기의 선택 전달 방식부터 작은 실험으로 검증한다. 파일 수·공백·한글·긴 경로·인자 길이 제한을 확인한 뒤 등록 방식을 확정한다.
- [ ] 필요하다면 선택 목록을 받는 Windows 연동 방식을 검토한다. 셸 확장 등이 필요할 경우 포터블 배포·등록/해제에 미치는 영향을 기록한 뒤 방식을 결정한다.
- [ ] 요구 범위 밖의 혼합 선택에서는 메뉴 숨김을 우선 검토하고, 실행 경로에도 검사를 넣어 잘못된 일괄 변환을 막는다.
- [ ] 선택된 파일을 한 작업 목록으로 구성하고 순서대로 변환한다. Office를 여러 개 동시에 실행하지 않는 방식으로 시작한다.
- [ ] 진행 중인 파일, 전체 개수, 완료 개수를 표시한다.
- [ ] 파일별 성공·실패·취소·결과 경로를 누적한다. 일부 실패가 전체 성공으로 표시되지 않게 한다.
- [ ] 일부 파일 실패 시 나머지를 계속 처리하고, 결과 요약에서 실패 원인을 확인할 수 있게 한다.
- [ ] 취소 시 남은 작업을 멈추고, 이미 완료된 결과와 원본은 보존한다.
- [ ] 필요한 Office/PPT 확인과 로그인 제안은 한 배치에서 반복하지 않는다. 브라우저는 사용자가 동의한 경우에만 연다.
- [ ] 기존 파란 안내·초록 성공·빨간 오류와 2.5초 알림 규칙을 유지한다. 자동 알림이 닫혀도 실패 상세를 확인할 경로를 확보한다.
- [ ] 기존 사용자는 프로그램의 메뉴 체크를 껐다 켜 새 등록을 적용할 수 있게 안내한다.

완료 기준: Windows 탐색기에서 단일 파일, 같은 확장자 2개, 20개 이상을 선택해 메뉴 표시·파일 전달·저장 결과를 확인한다. 일부 실패, 취소, 중복 파일명, 서로 다른 원본 폴더의 작업도 검증한다. 등록 문자열을 검사하는 단위 테스트만으로 완료 처리하지 않는다.

## 3단계 — Word → PDF

- [ ] `DOC`, `DOCX` 입력을 인식한다.
- [ ] 설치된 Word 또는 LibreOffice를 이용하는 변환 경로를 확인하고 작은 샘플로 검증한다.
- [ ] 기존 PowerPoint 전용 처리에 Word 처리를 무리하게 섞지 않고, 필요한 문서 유형만 구분한다.
- [ ] 미설치·암호·글꼴 누락·응답 지연·변환 실패를 친절하게 안내한다.
- [ ] 변환에 사용한 문서와 프로세스만 정리한다. 사용자가 열어 둔 Office 문서를 닫지 않는다.
- [ ] 메인 UI와 우클릭 단일/다중 변환에 연결한다.
- [ ] Word → PNG는 Word → PDF → 페이지 이미지 순서의 재사용 가능성을 검토한다.

완료 기준: DOC/DOCX 각각에서 일반 텍스트, 표, 이미지, 머리말·꼬리말, 여러 페이지 문서를 확인한다. 결과 파일 생성뿐 아니라 페이지와 주요 내용도 비교한다.

## 4단계 — PDF와 TXT·HTML·Markdown·이미지의 양방향 처리

### 4-0. PDF → TXT

- [ ] PDF 입력 형식 선택 목록과 우클릭 메뉴에 `TXT`를 추가한다.
- [ ] 페이지 순서대로 텍스트를 추출하고 UTF-8로 저장한다.
- [ ] 페이지 사이 구분을 유지하되, 원본의 글꼴·위치·표·이미지는 보존하지 않는다고 안내한다.
- [ ] 스캔 PDF에서 텍스트가 비어 있으면 OCR 기능과 혼동하지 않도록 안내한다.

완료 기준: 여러 페이지의 텍스트 순서, 한글, 빈 페이지, 암호 PDF 실패 처리를 확인한다.

### 4-1. PDF → HTML/Markdown

- [ ] 텍스트가 포함된 PDF부터 지원한다. 제목·문단·목록·읽기 순서·이미지 추출을 검증한다.
- [ ] 표와 다단 편집은 복원 한계를 표시하고, 빈 문서나 읽기 순서가 무너진 결과를 정상 성공으로만 안내하지 않는다.
- [ ] HTML/Markdown의 이미지 파일과 상대 경로를 함께 저장할 결과 폴더 규칙을 정한다.
- [ ] 스캔 PDF를 감지한다. OCR이 없는 상태에서는 텍스트 복원이 가능한 것처럼 안내하지 않는다.
- [ ] OCR은 언어 데이터·EXE 용량·정확도를 별도 검토한다. 검증 전에는 확정 지원으로 표시하지 않는다.

### 4-2. HTML/Markdown → PDF

- [ ] 로컬 HTML과 Markdown 파일 입력부터 지원한다.
- [ ] 렌더링 엔진의 포터블 포함 가능 여부, 배포 조건, 용량을 확인한다.
- [ ] Markdown → HTML → PDF 경로를 우선 검토해 렌더링 처리를 공유한다.
- [ ] 상대 경로 이미지, 한글·다국어 글꼴, 표, 코드 블록, 페이지 나눔을 확인한다.
- [ ] 외부 이미지·폰트·스크립트가 필요한 문서의 처리 방침을 정한다. 자동 업로드나 로그인 전제를 추가하지 않는다.
- [ ] HTML/Markdown → PNG는 위 PDF 출력과 기존 페이지 이미지 변환을 연결할 수 있는지 확인한다.

### 4-3. PDF↔PNG와 이미지 묶음

- [ ] 이미 구현된 PDF → 페이지별 PNG, 개별 PNG → PDF를 회귀 검증한다.
- [ ] PNG/JPG/TIFF 여러 파일을 하나의 PDF로 합치는 작업을 별도로 추가한다.
- [ ] 합치기에서는 페이지 순서·용지 크기·여백·출력 위치를 명시적으로 선택하게 한다.
- [ ] 우클릭의 일괄 개별 변환을 임의로 합치기 동작으로 바꾸지 않는다.

완료 기준: HTML/Markdown의 이미지 참조가 출력 폴더에서 정상 연결되고, 한글·표·페이지가 검증된다. PDF↔PNG 및 왕복 변환을 원본 편집 구조의 완전 복원이라고 표현하지 않는다.

## 5단계 — PDF → DOCX, 필요 시 DOC

- [ ] 편집 가능한 DOCX 생성을 우선 목표로 후보 엔진을 비교한다. 특정 라이브러리는 아직 확정하지 않는다.
- [ ] 일반 문단·표·다단·이미지·스캔 문서 샘플로 복원 수준을 확인한다.
- [ ] 이미지로만 만든 Word 문서를 편집 가능한 텍스트 복원과 구분한다.
- [ ] 스캔 문서는 OCR 지원 여부에 따라 제한을 안내한다.
- [ ] `DOCX로 변환 (손상 가능)` 고지를 적용한다.
- [ ] DOC 출력은 DOCX 생성 후 외부 Office 연동으로 가능한지 별도 확인한다. DOCX 지원이 곧 DOC 지원이라고 안내하지 않는다.

완료 기준: DOCX가 Word에서 열리고 주요 내용과 텍스트 편집 여부를 확인한다. 이미지뿐인 결과, 일부 누락, 표 배치 변경을 정확하게 안내한다.

## 6단계 — HWP/HWPX 지원 가능성 확인 후 구현

- [ ] HWP와 HWPX를 별도 입력 형식으로 조사한다.
- [ ] 한컴오피스 설치 환경의 공식 자동화·내보내기 지원, 사용 조건, 사용자 확인창과 배포 제약을 확인한다.
- [ ] HWP/HWPX 각각 PDF로 변환되는 최소 실험을 수행한다.
- [ ] 가능한 환경이 확인된 경우에만 설치 감지와 변환 경로를 제품에 연결한다.
- [ ] 한컴오피스 미설치 환경은 별도 엔진의 실제 호환성을 검증한 뒤 지원 여부를 결정한다. 클라우드 전송은 별도 동의 없이 추가하지 않는다.
- [ ] 표·수식·글꼴·개체·암호 문서와 자동화 확인창 때문에 멈추는 경우를 점검한다.

완료 기준: 검증한 형식·제품 버전·설치 조건을 명시한다. 지원하지 않는 환경에서는 필요한 조건을 안내한다. PDF → HWP는 현재 확정 범위가 아니며 별도 타당성 검토 대상으로 남긴다.

## 7단계 — 추가 변환 후보 검토

핵심 요청이 안정화된 뒤 아래 후보를 하나씩 평가한다. 여기의 항목은 구현 확정 목록이 아니다.

| 후보 | 검토 순서와 주의점 |
| --- | --- |
| RTF/ODT/OTT → PDF·DOCX | Word 계열 문서 연동 재사용 가능성부터 확인 |
| XLS/XLSX/ODS/CSV → PDF·CSV·XLSX | 시트 범위, 인쇄 영역, 수식과 서식 손실 기준 정의 |
| ODP/PPT/PPTX → PDF·이미지 | 기존 프레젠테이션 변환과 페이지 렌더링 재사용 검토 |
| SVG → PNG/JPG/PDF | 렌더러와 외부 리소스·글꼴 지원 확인 |
| TXT/HTML/Markdown 상호 변환 | 인코딩 및 서식 소실 고지 정의 |
| ZIP/7Z/TAR 내부 파일 일괄 변환 | 형식 변환과 압축 해제를 구분. 추출 경로·용량·정리 정책을 먼저 정하기 |

## 8단계 — 번역·문서·배포 마무리

- [ ] 기능별 새 문구를 16개 UI 언어에 반영하고 누락·자리표시자를 확인한다.
- [ ] 한국어·영어·일본어·중국어 간체·스페인어 README의 지원 표와 제한 사항을 맞춘다.
- [ ] `ROADMAP.md`에서 구현 완료된 항목과 계속 검토할 후보를 구분한다.
- [ ] 단위 테스트, 실제 Office/한컴 연동, Windows 탐색기 다중 선택 검증 결과를 따로 기록한다.
- [ ] 새 의존성의 배포 조건과 고지 파일, 소스 제공 관련 문서를 확인한다.
- [ ] 포터블 EXE에 새 번역·도우미·렌더링 자원이 포함되는지 검사한다.
- [ ] Python 없는 사용자 환경, 한글·공백 경로, 일반 사용자 권한, 재실행, 메뉴 등록/해제를 점검한다.
- [ ] EXE 자체 진단과 실행 확인 후 체크섬·소스 ZIP을 갱신한다.
- [ ] 단계별로 필요한 변경만 add/commit한다. push는 사용자가 직접 진행한다.
- [ ] GitHub Releases의 EXE 첨부 파일도 새 버전으로 교체해야 실제 다운로드가 갱신된다는 점을 안내한다.

## 작업 단위와 완료 판단

한 작업은 **재현 샘플 준비 → 최소 구현 → 실패·취소 검증 → 실제 결과 확인 → 번역·문서 반영 → 커밋** 순서로 진행한다.

첫 개발 작업은 **0~2단계와 PDF → TXT: 기준 상태 정리, 형식 값 분리와 품질 고지, PDF 텍스트 추출, 동일 확장자 다중 선택 변환**으로 잡는다. 이후 Word, PDF 문서 변환, HWP 순서로 진행한다. 각 단계의 완료 기준을 통과하지 못하면 해당 기능을 지원 완료로 표시하거나 배포하지 않는다.
